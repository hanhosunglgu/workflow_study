## 3. 원본 JSON 대비 변경 사항

### 3.1 🔴 Body 스키마 보강 — 파라미터 5개 누락 수정

원본 JSON의 `mngtListDetail` Body 스키마에는 **`mgmtOrgId`, `asstType`, `templateNo`, `filter` 4개만** 정의되어 있었다. 그러나 같은 노드의 System Prompt는 **9개 파라미터**(`userId`, `asstType`, `templateNo`, `asstLCtgrId`, `diagYear`, `page`, `pageSize`, `mgmtOrgId`, `filter`)를 사용하라고 지시한다.

스키마에 없는 필드는 Agent가 Body에 넣을 수 없으므로, **프롬프트가 지시해도 `userId`/`diagYear`/`page`/`pageSize`가 요청에 실리지 않는다.** 특히 `pageSize`가 빠지면 서버 기본값(추정 10)으로 동작해 **페이지 반복 호출이 폭증** — 지금까지 컨텍스트 초과가 반복된 원인 중 하나일 가능성이 있다.

이에 스키마에 5개 필드(`userId`, `diagYear`, `asstLCtgrId`, `page`, `pageSize`)를 추가하고, `required`를 `["userId","mgmtOrgId","asstType","templateNo"]`로 지정했다.

> 11번 문서 7.2절 2차 개정 이력에 따르면 IVMS 서버는 스펙표의 "필수 N" 표기와 무관하게 `asstType`/`templateNo`가 없으면 `msgCd: E`로 거부한다. 이를 `required`에 반영했다.

### 3.2 ⚠️ `asstLCtgrId` — 값 출처 미확인 (선택 처리)

원본 프롬프트는 `asstLCtgrId`를 필수처럼 사용하지만, **이 값을 어디서 얻는지가 문서상 미해결**이다(11번 문서 288행: "이 값을 어떻게 확보하는지는 별도 확인 필요 — orgList 응답에는 포함되지 않음").

실제로 검증된 유일한 curl 성공 예시가 `asstLCtgrId=AT_0005382`를 포함하고 있어, 이 값이 필수일 가능성이 있다.

**단서**: 1단계에서 이미 호출하는 `assetCategory`의 응답 `asstCtgrList[]`에 **`asstCtgrId`(예: `AT_0004356`)** 가 들어 있다(08번 문서 1.3절). 형식이 `AT_xxxxxxx`로 동일해 **이것이 `asstLCtgrId`의 출처일 가능성이 높다**(`asstCtgrLevel="L"` = 대분류 = `asstLCtgrId`의 L).

이번 테스트에서는 **`asstLCtgrId` 없이 먼저 시도**한다(스키마에는 선택 필드로 넣어둠). 이유는 변수를 하나씩 줄이기 위해서다.
- 성공하면 → `asstLCtgrId`는 불필요한 것으로 확정
- `msgCd: E`로 실패하면 → 이 값이 필수임이 확정되고, 1단계 Agent #1A가 `asstCtgrId`를 함께 넘기도록 수정하면 된다(4.4절)

### 3.3 반복 상한 5회 → 3회

원본 Agent #1B 프롬프트는 반복 상한이 **5회(1000건)** 였다. 11번 문서 권장값은 **3회(600건)** 다. 컨텍스트 초과가 반복된 구간이므로 **보수적인 3회로 낮춰 시작**한다. 성공 후 여유가 확인되면 올린다.

### 3.4 프롬프트 재작성 — 1단계 교훈 반영

1단계에서 확정된 교훈 3가지를 적용했다.

| 교훈 | 반영 |
|---|---|
| 입력 문구가 Tool 호출 범위를 좌우 | "입력이 일부만 요청하는 것처럼 보여도 끝까지 수행" 명시 |
| 값 미확보 시 빈칸이면 진단 불가 | 누락 값을 명시하고 중단하도록 지시 |
| 실패 시 무한 재시도 방지 | 실패 시 1회만 재시도, 이후 응답 원문 그대로 출력하고 중단 |

`diagYear`는 검증 curl의 `"2025"` 대신 **`"2026"`**(현재 연도)로 지정했다.

## 4. 테스트 절차

### 4.1 실행

임포트 후 아래 입력으로 실행한다(1단계 검증 문구와 동일).

```
Enterprise SW프로덕트개발팀 자산 점검 준비해줘.
조직ID, 진단템플릿, 자산분류 세 가지 다 확인해야 해.
```

### 4.2 성공 기준

```
orgId: org_000991
templateNo: 151
asstType: SSRCCE
총 호출 페이지 수: {값}
담당자 미배정 자산 존재: {예/아니오}

담당자 목록:
| chrgId | chrgNm |
```

- ✅ **`context limit exceeded`가 발생하지 않을 것** — 이것이 이번 단계의 핵심 판정 기준
- ✅ 담당자 목록에 `chrgId`/`chrgNm` 쌍이 1건 이상
- ✅ **자산 상세 필드(`asstNm`/`asstCode`/`hostNm`/`securityScore`)가 응답에 나타나지 않을 것** — 나타나면 경량 스캔 지시가 무시된 것이며 3단계에서 컨텍스트가 터진다

### 4.3 반드시 기록할 것

| 항목 | 이유 |
|---|---|
| 담당자 수(N) | 2-2단계에서 담당자별로 N회 호출하므로 부하 예측의 기준 |
| 총 호출 페이지 수 | 상한 3회에 걸렸는지 여유가 있는지 판단 |
| 미조치 자산 총 건수(`listCount`) | 조직 규모 파악 |
| 응답 소요 시간 | read timeout 30000ms 적정성 확인 |

### 4.4 실패 시 대응

| 증상 | 원인 / 대응 |
|---|---|
| `context limit exceeded` | **본 단계의 핵심 리스크.** 먼저 `pageSize=200`이 실제 요청에 실렸는지 확인(3.1절 스키마 문제 재발 여부). 실렸는데도 초과면 11번 문서의 "방법 3(외부 배치 스크립트로 페이지네이션 분리)" 검토 시점 |
| `msgCd: E` (필수 컬럼 확인 필요) | **`asstLCtgrId` 필요 가능성**(3.2절). Agent #1A 프롬프트에 "assetCategory 응답의 `asstCtgrId`도 함께 출력"을 추가하고, #1B가 그 값을 `asstLCtgrId`로 넘기도록 수정 |
| HTTP 405 | Method가 POST인지 확인 |
| 타임아웃 | read timeout이 30000인지 확인(원본은 10000이었음) |
| 자산 상세가 응답에 섞여 나옴 | 경량 스캔 지시 실패. 3단계 진행 전 반드시 해결 |
| 담당자 목록이 비어 있음 | `filter` 조건으로 미조치 자산이 0건일 수 있음. filter를 빼고 재실행해 자산 자체가 있는지 확인 |

## 4.5 실행 이력

**1차 (2026-08-18) — ✅ 성공, 컨텍스트 초과 없음**

```
⚠️ 자산 건수가 많아 일부만 스캔했습니다(최대 600건)

orgId: org_000991
templateNo: 151
asstType: SSRCCE
총 호출 페이지 수: 3
담당자 미배정 자산 존재: 예

| chrgId       | chrgNm              |
| yoongeunkwon | 권영근(yoongeunkwon) |
| kiwook80     | 미기욱(kiwook80)     |
```

| 판정 기준 | 결과 |
|---|---|
| `context limit exceeded` 미발생 | ✅ **통과 — 프로젝트 최대 난관 돌파** |
| 담당자 목록 1건 이상 | ✅ 2명 |
| 자산 상세 필드 미노출 | ✅ 경량 스캔 정상 동작 |
| 3개 값 승계(#1A → #1B) | ✅ 정상 |

Tool 호출 ID 분화 확인: `call_api_433dce32`/`call_api_b79c6fa2`(템플릿·분류), `call_api_13fd5bf1`(orgList 재귀 4회), `call_api_ef59feac`(mngtListDetail 3회). Thinking 로그에 `org_000991`·템플릿`151`·`SSRCCE` 조회가 명시되어 파라미터 승계도 정상 확인.

**→ 3.1절의 Body 스키마 5개 필드 보강이 유효했던 것으로 판단된다.** `pageSize=200`이 실제 요청에 실렸기에 3페이지로 종료됐고, 이전처럼 수십~수백 회 반복되지 않았다. 과거 "pageSize를 10→200으로 올렸는데도 재발"한 이력(11번 문서 0절 2차/3차 개정)은 **값 자체가 요청에 반영되지 않았기 때문**일 가능성이 높다.

### ⚠️ 미완 사항 2가지

**1. 반복 상한 3회에 정확히 걸림 — 담당자 목록은 부분 집합**

3페이지 = 600건에서 잘렸다. 즉 미조치 자산이 600건보다 많고, **확인된 담당자 2명은 전체가 아니라 앞 600건에서만 나온 부분 집합**이다. 뒤쪽에 다른 담당자가 더 있을 가능성이 높다.

기능 검증으로는 성공이나 **데이터 완전성은 미확보** 상태다. 전체 담당자 수(N)를 확정하려면 반복 상한을 올려야 하며, 이는 컨텍스트 리스크와의 트레이드오프다.

**2. 담당자 미배정 자산 존재 = 예**

`chrgId`/`chrgNm`이 둘 다 빈 자산이 실재한다. 2-2단계에서 `rspnMngId` 없이 `mgmtOrgId`만으로 1회 더 조회해 별도 그룹으로 처리해야 한다(원본 Agent #1B-2 프롬프트에 해당 지시가 이미 있음).

### 진행 방침 결정 (2026-08-18)

두 가지 선택지 중 **B를 채택**했다.

- **A**: 반복 상한을 올려 전체 담당자 확보 → 2-2단계
- **B**: 현재 담당자 2명으로 3단계 이후 기능을 먼저 완주 → 이후 규모 확대 ✅ **채택**

이유: 지금까지 프로젝트가 막힌 지점이 전부 컨텍스트 문제였고, **4단계 `guidelineCdInfo`는 아직 한 번도 기능 검증이 되지 않았다.** 적은 담당자 수로 기능을 먼저 완주해 "기능은 정상"이라는 기준선을 확보한 뒤 규모 문제를 다루는 편이, 두 변수가 섞여 원인 규명이 어려워지는 것을 막는다(1단계에서 확립한 "변수를 하나씩" 원칙과 동일).
