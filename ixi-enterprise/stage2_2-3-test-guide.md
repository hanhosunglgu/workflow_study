## 0. 왜 두 단계를 함께 준비하는가

3단계(`scanResultCodeMngtDetail`)는 **`asstCode` 목록을 입력으로 요구**하는데, 이 값은 2-2단계(담당자별 정밀조회)가 생산한다. 2단계의 경량 스캔은 담당자 ID만 남기고 자산 상세를 의도적으로 버리므로 `asstCode`가 없다.

따라서 순서는 반드시 **2-2단계 → 3단계**이며, 두 파일을 함께 만들되 **실행은 반드시 2-2단계부터** 한다.

## 1. 2-2단계 — 담당자별 정밀조회 (10노드 / 9엣지)

```
Chat Input → #1A → #1B(경량스캔) → #1B-2(정밀조회) → Chat Output
              ↑3 Tools    ↑mngtListDetail  ↑mngtListDetail(복제)
```

### 1.1 검증 대상

2단계가 확보한 담당자 2명(`yoongeunkwon`, `kiwook80`)을 순회하며 **`rspnMngId`로 담당자별 자산 상세를 수집**하는지 확인한다.

이 단계는 11번 문서 0절 3차 개정에서 컨텍스트 초과 대응으로 **신설했으나 한 번도 검증되지 않은 구간**이다.

### 1.2 원본 대비 변경

**🔴 `asstLCtgrId`를 `required`에서 제외**

원본 JSON의 `#1B-2` Body 스키마는 `asstLCtgrId`를 **필수**로 지정하고 있었다. 그러나 이 값은 **출처가 문서상 미해결**이며(11번 문서 288행), 2단계에서 이 값 없이 `mngtListDetail` 호출이 성공한 것이 이미 확인됐다.

필수로 두면 Agent가 값을 지어내거나 호출을 포기할 수 있으므로 선택 필드로 내렸다. `required`는 2단계 성공 조합에 `rspnMngId`만 더한 5개로 지정했다.

**프롬프트 재작성** — 2단계까지의 교훈 반영:
- 입력 문구 종속 방어 문구 추가
- 실패 시 1회만 재시도 후 원문 출력하고 중단(무한 재시도 방지)
- `asstCode`는 3단계 필수 입력이므로 누락 없이 보존하라고 명시
- 서버 필터 재검증 지시 유지(`mgmtOrgId` 불일치 자산 제외 — 08번 문서에 기록된 알려진 이슈)

### 1.2-1 🔴 실행 이력 1차 — 중괄호 템플릿 변수 오류 (2026-08-18)

첫 실행에서 Tool 호출이 하나도 없이 **실행 전 검증 단계에서 즉시 실패**했다.

```
'orgId' 필드의 'Agent' 노드의 'orgId' 항목이 비어 있습니다.
캔버스에서 해당 입력을 연결하거나 값을 선택해 주세요.
```

**원인**: Agent의 프롬프트 필드는 이름 그대로 **`System Prompt Template`** — 단순 텍스트가 아니라 템플릿이다. 따라서 `{orgId}` 같은 **중괄호 표기를 "채워야 할 입력 변수 선언"으로 해석**한다.

작성 당시 값이 들어갈 자리를 표시하려고 쓴 아래 표기들이 전부 변수 선언이 되어버렸다.

```
mgmtOrgId={orgId}, asstType={asstType}, templateNo={templateNo},
rspnMngId={현재 순회 중인 담당자의 chrgId}
=== {담당자명}({chrgId}) ===
```

플랫폼이 `{orgId}` 변수를 발견했으나 캔버스에 연결된 입력이 없으므로 실행 자체를 거부했다.

**대응**: 전 단계 파일(1/2/2-2/3단계)의 System Prompt에서 중괄호를 **모두 제거**하고 서술형으로 교체했다.

| 변경 전 | 변경 후 |
|---|---|
| `mgmtOrgId={orgId}` | `mgmtOrgId 에는 입력에서 파싱한 orgId 값` |
| `rspnMngId={현재 순회 중인 담당자의 chrgId}` | `rspnMngId 에는 현재 순회 중인 담당자의 chrgId 값` |
| `=== {담당자명}({chrgId}) ===` | `=== 담당자명(담당자ID) ===` + "실제 값으로 치환" 주석 |
| `{값}` | `실제 값` |
| `{예/아니오}` | `예 또는 아니오` |

> ⚠️ **이후 모든 프롬프트 작성 시 중괄호를 쓰지 말 것.** 1단계 v3 프롬프트는 `{값}` 하나만 반복돼 통과했으나(출력 형식부라 검증을 피한 것으로 추정), 2-2단계처럼 서로 다른 이름의 중괄호가 여럿 들어가면 즉시 검증 오류가 난다. 값 참조는 항상 서술형으로 표현한다.
>
> 이 제약은 11번 문서에도 반영이 필요하다 — 해당 문서의 System Prompt 원문들이 `{값}` 표기를 광범위하게 사용하고 있다.

### 1.2-2 🔴 실행 이력 2차 — 컨텍스트 예산 초과 (2026-08-18)

중괄호 문제 해결 후 재실행하자 `#1B-2`의 반복 조회 단계에서 초과했다.

```
context limit exceeded: estimated 1324532 tokens > budget 945000
```

**과거 이력과 규모가 다르다:**

| 시점 | 추정 토큰 | 예산 | 모델 |
|---|---|---|---|
| 과거 1차 | 120,032 | 100,000 | (구 모델) |
| 과거 2차 | 109,508 | 100,000 | (구 모델) |
| **이번** | **1,324,532** | **945,000** | `gpt-5.5` |

예산이 100k → 945k로 **9.45배 증가**한 것은 `gpt-5.5` 전환 효과로 보인다. 그러나 사용량이 **11배**로 더 크게 늘어 여전히 초과했다.

**원인**: 로그상 `call_api_b1d404b6`(#1B-2의 `mngtListDetail`)가 연속 호출되며 터졌다. 두 요인이 겹쳤다.

1. **2단계의 담당자 목록이 600건에서 잘린 부분 집합**이었는데, #1B-2가 그 담당자들을 `rspnMngId`로 재조회하며 **담당자당 최대 600건**을 다시 가져옴
2. #1B-2는 자산 상세 5개 필드(`asstNm`/`asstCode`/`hostNm`/`securityScore`/`timeEndYmd`)를 보존하므로, 2단계 경량 스캔(2개 필드)보다 **레코드당 컨텍스트 비용이 몇 배**

이는 11번 문서 0절 3차 개정이 이미 경고한 구조적 한계의 재확인이다 — **Agent를 쪼개도 한 Agent 안에서 페이지 반복 응답이 누적되는 문제는 해결되지 않는다.** #1B-2는 "담당자 단위로 좁히면 응답이 작아진다"는 가정으로 설계됐으나, 담당자 1명이 수백~수천 건을 보유하면 그 가정이 무너진다.

### 1.2-3 대응 — A+B 축소 적용 (2026-08-18)

기능 검증 우선 방침(옵션 B)에 따라 **데이터 완전성을 포기하고 규모를 강제 축소**했다.

| 축소 항목 | #1B-2 | #1C |
|---|---|---|
| 처리 대상 | **담당자 1명만**(맨 앞) | 입력 자산 **10건까지만** |
| 페이지 반복 | **1회 고정**(page 증가 금지) | **1회 고정** |
| 보존 필드 | `asstCode`, `hostNm` **2개만** | 4개 키 포함 **8개만** |
| 결과 상한 | **30건** 초과 시 절삭 | **15건** 초과 시 절삭 |
| 담당자 미배정 | 이번 단계 조회 안 함 | — |

절삭한 건수는 숫자로 보고하도록 해 데이터 손실을 인지할 수 있게 했다.

> ⚠️ **이 축소는 기능 검증 전용이다.** 4단계 `guidelineCdInfo` 검증까지 완주해 "기능은 정상"이라는 기준선을 확보하는 것이 목적이며, **운영 적용 가능한 구성이 아니다.** 규모 문제는 11번 문서의 "방법 3"(외부 배치 스크립트로 페이지네이션을 캔버스 밖에서 처리)으로 별도 해결해야 한다.

> 📌 **프롬프트 내 JSON은 중괄호를 써도 무방함이 확인됐다** — `filter={"xorStr":{...}}` 형태는 2단계에서 정상 실행됐다. 플랫폼이 변수로 인식하는 것은 `{orgId}`처럼 **단일 식별자 형태의 중괄호**뿐이다.

### 1.2-4 🔴 실행 이력 3차 — 축소 후에도 초과, 병목은 #1A였음 (2026-08-18)

A+B 축소 후 재실행 결과 수치는 줄었으나 여전히 초과했다.

```
1,324,532 → 1,017,179 토큰 (예산 945,000)
```

**중요: 터진 지점이 이전과 다르다.** 로그의 Thinking 내용이 전부 Agent #1A의 조직 탐색이었다.

```
"admin API 3건으로 조직ID 흐름을 좁혔고, 이제 템플릿·자산분류를 잇습니다"
"admin API 5건 호출로 조직ID 확인 후 템플릿·자산분류 조회를 이어갑니다"
"org 조회 API 6건 응답을 엮어 Enterprise SW프로덕트개발팀 조직ID를 확정 중입니다"
```

누적 호출 수가 "3건 → 5건 → 6건"으로 증가하는 것이 그대로 보이며, **#1B-2는 시작도 하지 못한 채 종료**됐다. 즉 방금 축소한 #1B-2/#1C가 아니라 **맨 앞 #1A의 `orgList` 재귀가 컨텍스트를 소진**하고 있었다.

**왜 이제야 드러났나**: 1·2단계에서도 `orgList`는 4~6회 호출됐으나 통과했다. 차이는 **파이프라인 길이**다. #1A → #1B → #1B-2로 이어지며 앞 단계 컨텍스트가 뒤로 계속 전달되고, 거기에 `orgList` 응답 원본(조직 배열)이 6회분 누적된다. 최상위부터 4단계를 훑으면 매 호출마다 수십~수백 개 조직 레코드가 쌓인다.

**교훈**: 축소 대상을 뒷단에서만 찾았으나 실제 병목은 **이미 검증을 마쳐 손대지 않던 앞단**에 있었다. 파이프라인이 길어지면 앞단의 비용이 뒤로 전파된다.

## 2. 3단계 — 취약점 상세 수집 (12노드 / 11엣지)

```
... → #1B-2 → #1C(scanResultCodeMngtDetail) → Chat Output
```

### 2.1 검증 대상

자산별 취약점 항목을 조회하고, **4단계가 요구하는 4개 키**(`guidelineIfKey`, `itemCode`, `agentServerNm`, `resultIfKey`)를 확보하는 것이 핵심이다. 이 4개가 없으면 4단계 `guidelineCdInfo`를 호출할 수 없다(11번 문서 0절).

### 2.2 원본 대비 변경

**⚠️ `severity="4"` 유지 — 필수 파라미터 (2026-08-18 정정)**

최초 작성 시 "기능 검증 단계이므로 필터로 결과가 0건이 되는 것을 막기 위해 `severity`를 지정하지 않는다"고 했으나, **실행 전 08번 문서 4.2절 입력 스펙을 재확인한 결과 `severity`는 필수(Y) 파라미터**임이 확인되어 정정했다.

```
| severity | 취약도 | string | Y | 4 | 1(최하)~5(최상) |
```

생략하면 호출이 거부될 가능성이 높으므로 **`"4"`(상)로 지정**하고, `required`에도 포함했다.

다만 08번 문서에 기록된 **severity 필터 신뢰성 이슈**는 그대로 유효하다 — `severity="4"`로 요청해도 응답에 `severity="5"` 항목이 섞여 오는 사례가 확인되어 있다. 이번 단계는 기능 검증이 목적이므로 **섞여 온 항목을 제외하지 않고 그대로 수집하되, 각 항목의 실제 severity 값을 있는 그대로 기록**하도록 지시했다. 필터링은 4단계 검증 완료 후 적용한다.

> 이 사례는 1단계 `asstType`(선택 필드라 첫 항목이 빈 값)과 같은 계열의 문제다. **프롬프트 작성 전 08번 문서 스펙표의 필수 Y/N을 반드시 대조할 것.**

**`required` 지정** — 원본은 `required`가 없어 Agent가 필수 파라미터를 빠뜨릴 수 있었다. 6개(`userId`, `asstCode`, `hostNm`, `resultStatusCdListStr`, `asstType`, `atemplateNo`)로 지정했다.

`resultStatusCdListStr="[\"FAIL\"]"`로 취약(미조치) 항목만 조회하는 것은 유지한다.

### 2.2-1 🔴 실행 이력 1차 — `msgCd: E` 필수 컬럼 확인 필요 (2026-08-18)

```
{"result":{"ifRslt":{"prssRsltMsg":"필수 컬럼 확인 필요.","prssRsltCd":"N"}},
 "msg":"필수 컬럼 확인 필요.",
 "_server_message_":{"text":"","type":"200","msgCd":"E"}}
```

HTTP는 `200`이고 서버가 비즈니스 로직 단계에서 거부했다. 파이프라인 자체는 정상이었다(#1A → #1B → #1B-2 통과, 마지막 `scanResultCodeMngtDetail`만 실패). 수집 항목 0건.

**진단의 제약**: ixi-enterprise 캔버스는 실제 요청 Body를 확인할 방법이 없다(07번 문서 REQ-009~012 — Execution Log/Input·Output 패널 부재). 따라서 어떤 파라미터가 문제였는지 로그로 특정할 수 없어, **08번 문서 4.2절의 검증된 성공 curl과 대조**하는 방식으로 좁혔다.

| 파라미터 | 검증된 성공 curl | 1차 요청 | 일치 |
|---|---|---|---|
| `userId` | `admin` | `admin` | ✅ |
| `asstCode` | `["SSRCCE3-000747","SSRCCE3-000492"]` (2건) | 10건 | 건수 차이 |
| `hostNm` | `["lbsh1","absdb1"]` | 10건 | 건수 차이 |
| `resultStatusCdListStr` | `"[\"FAIL\"]"` | 동일 | ✅ |
| `vadaYn` | `"N"` | 동일 | ✅ |
| `severity` | `"4"` | 동일 | ✅ |
| `asstType` | `"SSRCCE"` | 동일 | ✅ |
| `atemplateNo` | `"151"` | 동일 | ✅ |
| `page` | `1` | `1` | ✅ |
| **`pageSize`** | **`50`** | **`200`** | ❌ **불일치** |

**필수(Y) 3개(`userId`/`asstType`/`severity`)는 모두 전달됐으므로**, 스펙표상 필수가 아닌 항목에서 서버가 거부한 것이다. 이는 11번 문서 7.2절 2차 개정 이력의 `mngtListDetail` 사례와 같은 패턴이다 — **스펙표의 필수 N 표기와 무관하게 서버가 요구하는 파라미터가 존재한다.**

**대응**: 성공 조합과의 유일한 값 차이인 `pageSize`를 **`200` → `50`**(검증된 값)으로 되돌렸다. 아울러 `asstCode` 배치도 10건 → **5건**으로 줄여 성공 사례(2건)에 더 가깝게 맞췄다.

08번 문서 4.2절이 `severity`/`asstCode`/`hostNm` 항목마다 "데이터가 많아 오래 걸릴 수 있으니 좌측 데이터 샘플로 조회 바랍니다"를 반복 경고하는 점도 이 방향을 뒷받침한다.

> **다음 후보(이 대응이 실패할 경우)**: `asstLCtgrId`(자산분류 대). 08번 문서의 성공 예시에 `AT_0005393`이 포함되어 있고, `mngtListDetail`의 성공 조합에도 같은 값이 있었다.

### 2.2-2 ✅ 원인 확정 — 개발기 curl 진단 (2026-08-18)

캔버스는 요청 Body를 확인할 수 없어 진단이 막혔으므로, **개발기(`http://165.244.21.49:8080`)에 직접 curl을 날려** 파라미터를 1개씩 제거하며 원인을 특정했다(`scanresult-debug.sh`).

| 테스트 | 결과 | 판정 |
|---|---|---|
| T1 기준선 (`pageSize=50`) | ✅ 0건 | 조합 자체는 유효 |
| T2 `pageSize` 100 / 200 | ✅ 0건 | **`pageSize` 무관 — 1순위 가설 기각** |
| T3 without `atemplateNo` | ✅ 0건 | 선택값 맞음 |
| **T3 without `vadaYn`** | ❌ **FAIL** | **실제 필수** |
| **T3 without `hostNm`** | ✅ **8건** | **← 유일하게 데이터가 나온 케이스** |
| **T3 without `resultStatusCdListStr`** | ❌ **FAIL** | **실제 필수** |
| T3 without `page`/`pageSize` | ✅ 0건 | 선택값 맞음 |
| T4 `asstLCtgrId` 추가 | ✅ 0건 | **불필요 — 2순위 가설도 기각** |
| T5 스펙표 필수 3개만 | ❌ FAIL | 위 2개가 빠져서 |

**결론 2가지 — 둘 다 사전 가설과 달랐다.**

**① `vadaYn`과 `resultStatusCdListStr`이 실제 필수값**
08번 문서 스펙표는 둘 다 **선택(N)** 으로 기재하나 서버는 요구한다. 생략 시 `msgCd: E`. `mngtListDetail`에서 이미 겪은 것과 동일한 패턴이다(11번 문서 7.2절 2차 개정).

**② `asstCode`와 `hostNm`을 함께 보내면 결과가 0건이 된다**
`hostNm`을 제거하자 **8건이 정상 조회**됐다. 두 값이 AND 조건으로 걸려, 정확히 대응하지 않으면 교집합이 비는 것으로 보인다.

이는 #1C 프롬프트에 넣었던 아래 지시가 **틀렸음**을 의미한다.

> ~~"asstCode와 hostNm은 반드시 같은 순서로 대응하도록 함께 전달한다(한쪽만 전달하지 않는다)"~~

`asstCode`만으로 자산이 특정되므로 `hostNm`은 불필요하게 결과만 좁힌다. 08번 문서 4.2절의 성공 예시는 두 값이 정확히 대응하는 캡처였기에 동작했던 것으로 판단된다.

**대응 (반영 완료)**

| 항목 | 변경 |
|---|---|
| `hostNm` | **전달 금지** — 프롬프트·스키마 모두 명시 |
| `vadaYn` | `"N"` 고정, `required`에 추가 |
| `resultStatusCdListStr` | `"[\"FAIL\"]"`, `required`에 추가 |
| `pageSize` | 50 유지(값 제한 없음이 확인됐으나 보수적으로) |
| `required` | `userId`, `asstCode`, `resultStatusCdListStr`, `vadaYn`, `asstType`, `severity` |

> 📌 **08번 문서 4.2절에 이 발견을 반영 완료.** 스펙표 표기와 실제 서버 동작이 다른 사례가 `mngtListDetail`에 이어 두 번째로 확인됐다 — **IVMS API 전반에서 스펙표의 필수 Y/N 표기를 신뢰할 수 없다**고 보는 편이 안전하다.

> 📌 **진단 방식의 교훈**: 캔버스는 요청 Body를 볼 수 없어 원인 규명이 사실상 불가능했다. 개발기 curl 진단은 몇 초 만에 5개 가설을 판별했다. **앞으로 API 파라미터 문제는 캔버스에서 추측하지 말고 curl로 먼저 좁힐 것.**

`hostNm` 제거 + `vadaYn`/`resultStatusCdListStr` 필수 지정 반영 후 **취약점 정보 수집 성공.**

### 2.3 성공 기준

- ✅ `context limit exceeded` 미발생
- ✅ **4개 키가 모두 값으로 채워질 것** — `guidelineIfKey`, `itemCode`, `agentServerNm`, `resultIfKey`

**4단계 진행 불가**이므로 반드시 여기서 해결한다. 08번 문서 4.2절의 `scanRsltCodeList[]` 응답 필드를 대조해 필드명이 맞는지 확인한다. 1단계 `asstType` 사례처럼 **선택 필드(필수 N)라 특정 항목에서 비어 있을 가능성**도 함께 확인할 것.
