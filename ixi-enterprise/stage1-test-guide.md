## 1. 이번 단계에서 검증하는 것

사용자가 조직명을 입력하면 **Agent #1A가 3개 GET API만으로 `orgId`/`templateNo`/`asstType` 3개 값을 확정**하는지 확인한다.

담당자 조회, 미조치 자산 조회, 취약점 상세, 조치가이드 생성은 이번 단계의 검증 범위가 아니다.

**왜 이 단계를 분리하는가**: ixi-enterprise에는 단일 노드 독립 실행(Test Step)·Pin Data·Execution Log가 없어(`07-ixi-enterprise-requirements-spec.md` REQ-009~012), 노드를 추가할 때마다 Chat Input부터 전체를 재실행해야만 동작을 확인할 수 있다. 14노드를 한꺼번에 실행하면 실패 시 원인 노드를 특정하기 어렵다.

## 2. 테스트 구조 (6노드 / 5엣지)

```
Chat Input
  └─(message)→ Agent #1A ─(response)→ Chat Output
                  ↑ tools
      ┌───────────┼───────────┐
  orgList  assetSsrcceTemplate  assetCategory
   (GET)        (GET)             (GET)
```

원본 14노드에서 Agent #1B / #1B-2 / #1C / #2와 POST 계열 Tool 4개(`mngtListDetail` ×2, `scanResultCodeMngtDetail`, `guidelineCdInfo`)를 제거하고, 원본에는 없던 **Agent #1A → Chat Output 엣지를 추가**했다(원본은 Agent #1A → Agent #1B로 이어짐).

| 노드 | 설정 |
|---|---|
| Agent #1A | `azure_openai:gpt-5.4-mini`, temperature 0.5 |
| orgList | GET, connect 1000 / read 3000 |
| assetSsrcceTemplate | GET, connect 1000 / read 3000 |
| assetCategory | GET, connect 1000 / read 3000 |

> 이번 단계는 GET 3개만 사용하므로 POST 계열의 Read Timeout 30000ms 이슈(11번 문서 1절)와 무관하다. 다만 GET 3개의 read timeout이 3000ms로, 11번 문서가 권장하는 10000ms보다 짧다 — 4절 실패 대응 참고.

## 3. 원본 대비 변경 사항 (2건)

### 3.1 노드 축소 — 14개 → 6개

검증 대상이 아닌 노드를 제거했다. 원본 파일은 그대로 보존되어 있다.

### 3.2 Tool 호출 순서 재배치 (v2)

원본 프롬프트는 조직 탐색을 먼저 하고 그 뒤에 `assetSsrcceTemplate`/`assetCategory`를 호출하는 구조였다. 이 순서로는 **뒤의 두 Tool이 호출되지 않는 문제가 실측으로 확인됐다**(4절 실행 이력 참고).

v2에서는 순서를 뒤집어 **템플릿/분류 조회를 먼저, 조직 탐색을 나중에** 수행하도록 재배치했다.

근거: `assetSsrcceTemplate`과 `assetCategory`는 `userId`만 필요하고 **`orgId`에 의존하지 않는다**(08번 문서 1.2절/1.3절). 조직 탐색 뒤에 매달아둘 기술적 이유가 없으므로, 재귀 조회에 휩쓸려 누락되는 구조 자체를 제거했다.

아울러 다음을 함께 수정했다.
- 조건부 문장("orgId를 확정했으면 이어서 ~를 호출한다")을 제거하고 `[작업 1]`~`[작업 4]` 독립 단계로 분리
- "3개 값이 모두 채워지지 않았으면 아직 완료된 것이 아니다"라는 종료 조건을 명시
- 조직 탐색 실패 시에도 나머지 2개 값은 출력하도록 변경(기존에는 "찾을 수 없습니다"만 응답하고 종료)

> **재귀 시작점 `org_002205`는 원본 그대로 유지한다.** 최초 작성 시 08번 문서 1.6절/2.4절의 기록(`org_000991`의 `pOrgId`가 `org_000001`, `orgIdPath`가 `org_000001 / org_000991`)을 근거로 `org_000001`로 바꿨으나, **실측 결과 `org_002205`가 올바른 시작점**임이 확인되어 되돌렸다(4절 실행 이력 1차/2차 비교). 08번 문서의 해당 조직 계층 기록은 현재 조직 구조와 일치하지 않는 것으로 보이며, 별도 정정이 필요하다.

## 4. 테스트 절차

### 4.1 임포트

1. ixi-enterprise 캔버스에서 **새 워크플로우 생성 → 임포트**
2. `stage1-orgid-test.json` 선택
3. 노드 6개, 연결선 5개가 정상 표시되는지 확인

### 4.2 실행

Chat Input에 아래 문장을 입력하고 전체 플로우를 실행한다.

```
Enterprise SW프로덕트개발팀 조직 ID 확인해줘
```

### 4.3 성공 기준

응답에 아래 3개 값이 모두 포함되어야 한다.

| 항목 | 기대값 | 출처 |
|---|---|---|
| `orgId` | `org_000991` | 08번 문서 1.6절 실제 응답 |
| `templateNo` | (templateList[0].atemplateNo) | 08번 문서 1.2절 — 고정 기대값 없음, 값이 채워지기만 하면 성공 |
| `asstType` | (asstCtgrList[].asstType) | 08번 문서 1.3절 — 동일 |

Agent #1A의 프롬프트는 다음 형식으로 출력하도록 지시하고 있다:

```
orgId: {값}
templateNo: {값}
asstType: {값}
```

단, **문장 형식은 강제하지 않는다** — 11번 문서 7.1절 개정 이력에 따르면 응답 형식을 강제하는 지시가 Tool 호출 흐름과 충돌해 실패를 유발한 사례가 있다. 3개 값이 식별 가능하게 들어 있으면 성공으로 본다.

### 4.4 실패 시 점검 순서

| 증상 | 우선 점검 |
|---|---|
| "해당 조직명을 찾을 수 없습니다" | 재귀 시작점(3.2절). `pOrgId="org_000001"`인지 확인. 최대 4단계 순회 상한에 걸렸는지도 확인 |
| Tool 호출 자체가 안 됨 | 각 API Request 노드의 **Tool Mode가 ON**인지, Tools 포트에 실제 연결선이 있는지 |
| 타임아웃 / 응답 없음 | GET 3개의 read timeout이 3000ms로 짧다. 11번 문서 권장값 **10000ms**로 상향 후 재시도 |
| `templateNo`/`asstType`이 비어 있음 | `userId="admin"`으로 호출되는지 확인(프롬프트에 명시됨). `assetCategory`는 `asstCtgrLevel="L"` 필요 |
| 인증 오류 | **인증 헤더 4종은 빈 값으로 정상 동작함이 확인됨**(2026-08-18, 11번 문서 1절). 헤더 값 채우기보다 위 항목을 먼저 점검할 것 |

> 인증 헤더는 이번 단계에서 실패 원인이 아니다. 과거 문서가 서명 만료를 우선 의심하도록 안내했으나 그 가설은 배제됐다(11번 문서 1절 개정 이력).

### 4.5 실행 이력

**1차 (원본 프롬프트 + 시작점을 `org_000001`로 변경) — 실패**

```
orgId: org_001463    ← 잘못된 조직
templateNo:          ← 빈 값
asstType:            ← 빈 값
```

- Tool 호출 4회, **전부 동일 ID(`call_api_22b63dd8`)** = `orgList`만 반복 호출
- `assetSsrcceTemplate`/`assetCategory`는 호출 이력 없음
- → 시작점을 `org_000001`로 바꾼 것이 오판이었음이 드러남

**2차 (시작점을 원본 `org_002205`로 복원) — 부분 성공**

```
orgId: org_000991    ✅ 정확
templateNo:          ← 빈 값
asstType:            ← 빈 값
```

- Tool 호출 4회, **전부 동일 ID(`call_api_ad6cce75`)** = 여전히 `orgList`만 반복
- Thinking 로그가 전부 조직 탐색 내용("상위 조직 `org_002205` 기준 ID 확인", "조직 유형별 응답 대조해 팀 ID 좁히는 중")
- **Tools 포트에 3개 Tool이 모두 정상 연결되고 Tool Mode도 전부 ON임을 캔버스에서 확인** → 연결 문제가 아님
- → `orgId` 탐색 자체는 정상. Agent가 `orgId` 확정 시점에 작업이 끝났다고 판단하고 후속 지시(2문단)에 도달하지 못한 것으로 판단

**원인 분석**: 원본 프롬프트는 (1) 1문단이 "~할 때까지 orgList를 호출한다"로 목표를 `orgId` 확정 하나로 못박고, (2) 2문단이 "확정했으면 이어서"라는 조건부 문장이라 앞 작업의 부속 절차처럼 읽히며, (3) 재귀가 4턴 이어져 대화가 길어질수록 뒤 문단의 비중이 떨어지는 구조였다.

**3차 (v2 프롬프트 — 호출 순서 재배치, 입력 "자산 확인해줘") — 부분 성공**

```
orgId: org_000991    ✅ 정확
templateNo: 151      ✅ 신규 성공
asstType:            ❌ 빈 값
```

- Tool 호출 ID가 처음으로 **3종류**로 갈림(`call_api_dbacbb71` ×4 = orgList, `call_api_3962cf3e` ×1, `call_api_3887cdb8` ×1)
- → v2의 호출 순서 재배치가 효과를 냈음이 확인됨. `templateNo` 확보 성공
- 마지막 호출 직후 바로 응답 종료 → `asstType`은 **호출은 됐으나 값 추출에 실패**

**🔑 3차에서 발견된 핵심 사실 — 사용자 입력 문구가 Tool 호출 범위를 좌우한다**

| 입력 문구 | 결과 |
|---|---|
| "조직 ID 확인해줘" | `orgList`만 호출, 후속 API 미호출 |
| "자산 확인해줘" | Tool 3개 모두 호출 |

즉 1차·2차 실패는 프롬프트 구조만의 문제가 아니었다. **System Prompt가 3개 작업을 지시해도, 사용자 메시지가 작업 범위를 좁게 표현하면 그쪽이 우선한다.** 실제 운영에서는 담당자가 자유롭게 입력하므로 이 종속성 자체가 리스크다 → v3에서 "사용자 입력이 일부 작업만 요청하는 것처럼 보여도 3개를 전부 수행한다"는 지시로 대응.

**`asstType` 빈 값의 원인 (08번 문서 1.3절 대조 결과)**

`assetCategory`의 Tool 설정과 파라미터는 정상이었다(`userId`, `asstCtgrLevel` 2개, `asstCtgrLevel="L"`은 스펙상 유효값 — 종류 `L/M/S`). 문제는 **응답 배열에서 값을 고르는 규칙**이었다.

08번 문서 1.3절 스펙표에서 `asstCtgrList[].asstType`은 **필수 N(선택 필드)** 이다. 즉 항목에 따라 비어 있거나 없을 수 있다. 그런데 v2 프롬프트는 "여러 개면 **첫 번째 값을 사용**"이라고 지시했으므로, 첫 항목의 `asstType`이 비어 있으면 그대로 빈 값이 된다.

→ v3에서 "`asstType`이 비어 있지 않은 **첫 번째** 항목을 사용"으로 수정. 전 항목이 비어 있으면 원인 파악용으로 배열 항목 수와 첫 항목의 `asstCtgrNm`을 함께 출력하도록 지시.

> 실제 값은 `SSRCCE`로 추정된다 — 08번 문서 1.3절 응답 예시(`"asstType": "SSRCCE"`), 그리고 `assetSsrcceTemplate` API 이름과도 일치한다.

**4차 (v3 프롬프트 + 모델 `gpt-5.5`로 변경) — ✅ 성공**

```
orgId: org_000991      ✅
templateNo: 151        ✅
asstType: SSRCCE       ✅
```

- Tool 호출 ID 3종류 확인(`call_api_a0563421` ×1, `call_api_a684a747` ×1, `call_api_f8b449d7` ×다수) — 3개 Tool 모두 호출됨
- Thinking 로그도 3개 작업을 모두 인지("admin 조회 후 조직ID·템플릿·자산분류 확인", "3건 API 호출 결과를 묶는 중")
- `asstType`은 08번 문서 1.3절 응답 예시에서 추정한 `SSRCCE`와 실제로 일치
- 입력 문구: `"Enterprise SW프로덕트개발팀 자산 점검 준비해줘. 조직ID, 진단템플릿, 자산분류 세 가지 다 확인해야 해."`

> ⚠️ **변수 2개가 동시에 변경됨**: 이번 실행은 v3 프롬프트와 모델 변경(`gpt-5.4-mini` → `gpt-5.5`)이 함께 적용됐다. 따라서 성공 요인이 프롬프트 개선인지 모델 상향인지 이 결과만으로는 분리되지 않는다. 1단계 목적(값 확보)은 달성했으므로 추가 분리 실험은 하지 않되, **2단계 이후 모델 선택 시 참고할 정보로 남긴다** — `gpt-5.5`가 다단계 Tool 호출을 안정적으로 처리하는 것으로 보인다.

> ⚠️ **`orgList` 재귀 호출 횟수가 이전 시도보다 증가**했다(`call_api_f8b449d7` 다수 호출). 1단계에서는 문제없지만, **2단계에서는 이 호출 응답들이 모두 Agent 컨텍스트에 누적**되므로 예산 초과의 한 요인이 될 수 있다.

## 7. 1단계 최종 확정값 (2026-08-18)

2단계 이후에서 그대로 사용하는 값이다.

| 항목 | 확정값 |
|---|---|
| `orgId` | `org_000991` (Enterprise SW프로덕트개발팀) |
| `templateNo` | `151` |
| `asstType` | `SSRCCE` |
| 재귀 시작점 | `pOrgId="org_002205"` (Enterprise 서비스개발Lab) |
| 검증 모델 | `azure_openai:gpt-5.5` |

**1단계에서 확정된 교훈 3가지**

1. **사용자 입력 문구가 Tool 호출 범위를 좌우한다** — System Prompt의 지시보다 사용자 메시지의 범위 표현이 우선하는 경우가 있다. 뒤 단계 Agent에도 동일 리스크가 있으므로 각 Agent 프롬프트에 "입력이 일부만 요청하는 것처럼 보여도 전부 수행" 지시를 넣어야 한다.
2. **`orgId`에 의존하지 않는 API는 조직 탐색보다 먼저 호출**해야 한다 — 재귀 조회 뒤에 매달면 누락된다.
3. **선택 필드(필수 N)는 "첫 번째 항목" 규칙으로 뽑으면 빈 값이 나올 수 있다** — `asstType`처럼 선택 필드는 "값이 비어 있지 않은 첫 번째 항목"으로 지시해야 한다. 08번 문서 스펙표의 필수 Y/N 표기를 프롬프트 작성 시 반드시 확인할 것.
