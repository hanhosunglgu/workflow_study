## 1. 이번 단계에서 검증하는 것

3단계가 확보한 4개 키로 **항목별 조치가이드(`measure`)를 조회**하는지 확인한다.

**API 자체는 개발기 curl로 이미 검증 완료**(2026-08-18). 이번 단계에서 새로 확인하는 것은 **캔버스에서 #1C가 4개 키를 정확히 넘겨 호출하는지**다.

### 사전 검증 결과 (curl)

```
guidelineCd  : DBM-001
guidelineNm  : 취약하게 설정된 비밀번호 존재
measure      : 569자 — 【점검방법】/【조치방법】 + 실제 명령어 포함
```

| 확인 항목 | 결과 |
|---|---|
| 필수 5개 파라미터 | 스펙표 표기 정확 — 하나라도 빠지면 `msgCd: E` |
| "파라미터 무관 응답" 이슈(09번 문서 5.3절) | **재현되지 않음** — `guidelineCd` 변경 시 응답도 변함 |
| 🔴 빈 응답 실패 모드 | **발견** — 키가 안 맞으면 HTTP 200 + 전 필드 빈 문자열 |

## 2. 구조 (10노드 / 9엣지)

```
Chat Input → #1A(하드코딩) → #1B → #1B-2 → #1C → Chat Output
                              ↑      ↑        ↑ tools
                         mngtList  mngtList2  ├─ scanResultCodeMngtDetail
                                              └─ guidelineCdInfo  ← 이번에 추가
```

3단계 파일에 `guidelineCdInfo` Tool 1개를 #1C의 Tools 포트에 추가한 구성이다. 신규 Agent를 만들지 않았다 — `guidelineCdInfo`는 항목당 1회 호출이고 응답이 배열이 아니라 단일 객체라, 별도 컨텍스트로 분리할 실익이 작다.

| Tool | Method | Timeout | Query Params |
|---|---|---|---|
| `guidelineCdInfo` | GET | read 10000 | `aresultNo`, `guidelineIfKey`, `guidelineCd`, `itemCode`, `agentServerNm` |

## 3. #1C 프롬프트 변경 사항

3단계 프롬프트에 **[작업 2]** 를 추가했다.

| 항목 | 내용 |
|---|---|
| 조회 범위 | 취약점 항목 **3건까지만**(기능 검증 목적, 컨텍스트 절약) |
| 키 매핑 | `resultIfKey` → `aresultNo` (나머지 4개는 이름 동일) |
| 🔴 같은 행 원칙 | 5개 값을 **반드시 같은 항목에서** 가져올 것 — 섞으면 빈 응답 |
| 🔴 빈 응답 방어 | `measure`가 빈 문자열이면 **"조회 실패(빈 응답)"** 로 표시. 성공 처리 금지 |
| 요약 | `measure`의 【조치방법】 섹션만 200자 이내로 발췌 |
| 제외 | `criteria`/`analysisInfo`/`measureDetailOrigin`은 응답에 포함 안 함(길이가 매우 김) |

> **빈 응답 방어가 이번 단계의 핵심이다.** 이 API는 키가 맞지 않아도 오류를 내지 않으므로, 방어 로직이 없으면 Agent가 조치가이드를 못 받았는데도 성공으로 처리한다.

## 4. 테스트 절차

입력은 1~3단계와 동일하게 유지한다(변수 고정).

```
Enterprise SW프로덕트개발팀 자산 점검 준비해줘.
조직ID, 진단템플릿, 자산분류 세 가지 다 확인해야 해.
```

### 성공 기준

```
orgId: org_000991
templateNo: 151
asstType: SSRCCE
조회한 담당자: 권윤근(yoongeunkwon)
수집한 취약점 항목 수: N
조치가이드 조회 성공 건수: N      ← 1건 이상이어야 성공
조치가이드 조회 실패(빈 응답) 건수: N
조회하지 않고 넘어간 항목 수: N

| asstCode | guidelineCd | guidelineNm | severity | 조치방법 요약 |
```

- ✅ `context limit exceeded` 미발생
- ✅ **조치가이드 조회 성공 건수 ≥ 1**
- ✅ 조치방법 요약에 실제 내용이 들어갈 것(【조치방법】 발췌)

### 실패 시 대응

| 증상 | 대응 |
|---|---|
| 전부 "조회 실패(빈 응답)" | 5개 키를 **같은 항목에서** 가져왔는지 확인. #1C가 서로 다른 행의 값을 섞었을 가능성. 3단계 출력 표에서 키가 정확히 보존됐는지 먼저 확인 |
| `msgCd: E` | 5개 중 하나가 누락됐거나 빈 값. 특히 `resultIfKey`→`aresultNo` 매핑 확인 |
| `context limit exceeded` | 항목 3건 상한이 지켜졌는지 확인. `criteria`/`analysisInfo`를 응답에 포함했다면 그것이 원인(각 500~650자) |
| 조치방법 요약이 비어 있음 | `measure`는 있는데 【조치방법】 섹션이 없는 항목일 수 있음 — 프롬프트가 앞부분 요약으로 fallback 하도록 되어 있으니 그것도 안 되면 원문 길이 확인 |

> 실패 시 `guideline-debug.sh`로 해당 항목의 5개 키를 직접 넣어 curl 호출해 보면, 캔버스 문제인지 데이터 문제인지 즉시 갈린다.

## 4.5 실행 이력 — ✅ 성공 (2026-08-18)

```
orgId: org_000991
templateNo: 151
asstType: SSRCCE
조회한 담당자: 권윤근(yoongeunkwon)
수집한 취약점 항목 수: 11
컨텍스트 절약을 위해 버린 항목 수: 0
조치가이드 조회 성공 건수: 3
조치가이드 조회 실패(빈 응답) 건수: 0
조회하지 않고 넘어간 항목 수: 8
```

| 판정 기준 | 결과 |
|---|---|
| `context limit exceeded` 미발생 | ✅ 통과 |
| 조치가이드 조회 성공 ≥ 1 | ✅ **3건 전부 성공** |
| 빈 응답 실패 | ✅ 0건 — 5개 키 매핑 정확 |

**"조회하지 않고 넘어간 항목 수: 8"은 정상 동작이다.** 프롬프트의 3건 상한(3절)에 따라 11건 중 3건만 조회한 결과이며(11 − 3 = 8), 오류가 아니다.

> **3건 상한의 근거**: `guidelineCdInfo` 응답은 항목당 `criteria`(487자) + `analysisInfo`(645자) + `measure`(569자) + `measureDetailOrigin`(2383자) ≈ **4천 자**로 무겁다. 11건 전량이면 4만 자 이상이 누적된다. 컨텍스트 초과가 3회 반복된 이력을 감안해 보수적으로 설정했다.

> 📌 **미측정 사항**: 이번 실행에서 컨텍스트 여유가 얼마나 남았는지는 확인되지 않았다(로그에 토큰 사용량 미표시). 규모 확대 시 상한을 3 → 6~8 → 11로 **단계적으로** 올리며 측정할 것. 한 번에 전량으로 올리면 초과 위험이 있다.

**→ 4단계 완료로 플로우 A의 IVMS 데이터 수집 체인(1~4단계) 전체가 검증됐다.**

## 5. 이 단계 이후

4단계 성공 시 **플로우 A의 IVMS 데이터 수집 체인이 전부 검증 완료**된다.

### 남은 작업

| 항목 | 상태 |
|---|---|
| 5단계 (Agent #2 + Human Approval + Language Model) | 원본 JSON에 Human Approval·Language Model **노드 자체가 없음** — 신규 배치 필요 |
| #1A 하드코딩 되돌리기 | `orgList` 재귀 복원. 단, 이 재귀가 컨텍스트 병목이므로 캐싱/시작점 축소 대책 필요 |
| 규모 확대 | 현재 담당자 1명 / 자산 30건 / 취약점 3건으로 강제 축소된 상태 |

### 5단계에서 되살려야 할 필드

컨텍스트 절약을 위해 #1B-2에서 버린 필드 중 **압박메시지 작성에 필요한 것**들이다.

| 필드 | 용도 |
|---|---|
| `securityScore` | 심각도 표시 |
| `timeEndYmd` | 경과일 계산(7일 이상 미조치 판단) |
| `asstNm` | 자산명 표기 |
| `hostNm` | 자산 식별(3단계 API에는 전달 금지, 출력에는 필요) |

> ⚠️ 이 필드들을 되살리면 컨텍스트 사용량이 다시 늘어난다. 5단계 진행 시 담당자 1명 기준으로도 예산을 초과하는지 재확인이 필요하다.
